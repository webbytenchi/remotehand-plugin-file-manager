# RemoteHand File Manager v0.1.0 Design

Status: **Accepted for implementation**

This document defines the first implementation milestone for RemoteHand File Manager.

The goal of v0.1.0 is to establish a reliable local-filesystem browser and file-operation foundation without trying to become a full desktop shell or Windows Explorer replacement.

## Product principles

- Local filesystem first.
- Windows-first implementation and acceptance testing, while keeping Windows + Linux portability in the design.
- Programmer/sysadmin-oriented behavior.
- Fast, predictable navigation.
- Safe file operations.
- RemoteHand core owns generic plugin infrastructure; File Manager owns filesystem-management semantics.
- Do not add speculative RemoteHand core APIs solely for this plugin.

## Layout

### First load

File Manager opens in **single-pane** mode on first use.

The user can switch between:

- single-pane
- dual-pane

The selected layout is persisted.

### Pane state

Each pane maintains its own:

- current path
- Back history
- Forward history
- selection
- sort state

One pane is the **active pane** in dual-pane mode.

Switching from dual-pane back to single-pane hides the second pane without discarding its state. Returning to dual-pane restores it.

The implementation should use one reusable pane model/component and render one or two panes rather than maintaining separate single-pane and dual-pane architectures.

## Initial view

Each pane uses a details/table presentation.

Initial columns:

- Name
- Type
- Size
- Modified

Directories should sort and display predictably. Column sorting should support the fields above.

Other view modes such as large icons, tiles, or thumbnails are deferred.

## Navigation

Each pane provides:

- Back
- Forward
- Parent
- Refresh
- path/breadcrumb bar

### Path bar

The path area normally appears as clickable breadcrumb segments.

The user can switch it to editable text input, type a path, and press Enter to navigate.

Invalid or inaccessible paths must produce a useful error without losing the previous valid location.

### Mouse behavior

- Double-click a folder to enter it.
- Double-click a file to open it with the operating system's default application.

### Keyboard shortcuts

Initial shortcuts:

- Alt+Left — Back
- Alt+Right — Forward
- Alt+Up — Parent
- F5 — Refresh
- Ctrl+L — focus/edit path

Keyboard navigation should remain a first-class design concern as the plugin grows.

## File operations

v0.1.0 includes:

- New Folder
- Rename
- Copy
- Move
- Delete
- Properties
- Copy Path
- Copy Filename

### New Folder

Create a folder in the active pane's current directory.

Validate names according to the current platform and report conflicts/errors clearly.

### Rename

Rename a single selected file or folder.

Batch rename is deferred.

### Copy and Move

Copy and Move must use a file-operation/job model rather than blocking the UI.

The architecture should be able to support:

- current item/path
- progress
- bytes completed / total where measurable
- item counts where measurable
- cancellation
- errors
- partial failures
- conflict handling

The first implementation may expose these incrementally, but Copy/Move must not be designed as synchronous UI-only actions that would require replacement later.

### Dual-pane operations

When dual-pane mode is active, expose:

- Copy to Other Pane
- Move to Other Pane

The active pane is the source and the other pane is the destination.

These explicit actions remain useful even after drag-and-drop is introduced.

### Delete

Normal Delete should prefer Recycle Bin / Trash semantics where supported by the platform.

Permanent delete is not part of v0.1.0.

Deletion must be conservative and clearly communicate what will be removed.

### Properties

Properties are read-only in v0.1.0.

Show useful metadata where available, including:

- name
- full path
- type
- size
- modified time
- created time where supported

Platform-specific metadata may be added later when justified.

### Copy Path / Copy Filename

Provide explicit commands for copying:

- full path
- filename only

These are core programmer/sysadmin conveniences.

## Hidden files

Support a user-controlled hidden-files toggle.

The implementation must respect platform differences:

- Windows hidden/system attributes where appropriate
- Linux dotfiles

Do not pretend these concepts are identical across platforms.

## File and directory handling

### Symlinks

Symlinks must be treated conservatively.

The plugin should:

- distinguish links from ordinary entries
- avoid blindly following links during recursive operations
- avoid surprising recursive delete/copy behavior
- preserve room for showing link targets later

### Special files

On Linux and other supported platforms, non-regular filesystem entries should not be assumed to behave like ordinary files or directories.

Unsupported operations should fail safely and explain why.

## Persistence

v0.1.0 should persist at least:

- single-pane vs dual-pane preference
- pane paths
- active pane
- per-pane sort state
- hidden-files preference

Back/Forward history persistence across full RemoteHand restarts is optional for v0.1.0; runtime history is required.

## Drag-and-drop

Drag-and-drop is intentionally **deferred until after the core Copy/Move job engine is reliable**.

The planned first drag-and-drop scope is internal File Manager drag-and-drop:

- between panes
- onto folders

When implemented, drag-and-drop must call the same trusted Copy/Move operation engine rather than creating separate filesystem behavior.

The preferred initial drop UX is an explicit action choice:

- Copy here
- Move here
- Cancel

OS-level drag-and-drop interoperability with Explorer, desktop, or arbitrary external applications is deferred.

## Deferred features

Not part of v0.1.0:

- drag-and-drop
- folder tree sidebar
- directory tabs
- batch rename
- permanent delete
- archive create/extract
- checksum calculation
- recursive directory-size calculation
- permission editing
- directory comparison
- rich previews
- full filesystem search/indexing
- cloud-storage providers
- remote filesystem providers
- external OS drag/drop
- File Manager -> Editor integration
- SFTP -> Editor remote-save integration
- generic action/intent contracts not yet required by concrete integrations

## Future Editor and SFTP integration

The intended future workflow remains:

```text
File Manager -> Open in Editor
Editor -> Show in File Manager
```

and later:

```text
SFTP -> Open in Editor -> edit -> Save -> write back to remote path
```

These integrations must remain generic and capability-driven rather than hard-coding Editor or SFTP semantics into File Manager or RemoteHand core.

No new core API should be introduced until concrete implementation work proves it is needed.

## First implementation slice

The first vertical slice should prove the browser foundation:

1. plugin loads in RemoteHand
2. one pane renders
3. current directory is listed
4. folders can be entered
5. Back works
6. Forward works
7. Parent works
8. Refresh works
9. path bar navigation works
10. basic Details columns render correctly

After that slice is manually accepted, add dual-pane switching/state, then file operations in small testable increments.

## Acceptance style

Development should follow the normal RemoteHand workflow:

- small purposeful commits
- automated checks for each meaningful slice
- regression tests for discovered edge cases
- one focused manual acceptance step at a time
- live output and observed behavior are authoritative
- avoid giant manual checklists or unnecessary full-suite runs

This document is the accepted v0.1.0 scope. Changes to the milestone should be deliberate rather than silently expanding implementation scope.
